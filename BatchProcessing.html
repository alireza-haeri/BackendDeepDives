پردازش دسته‌ای Batch Processing

داده را یک‌جا، به‌صورت یک شغل، پردازش کنید — نه رکورد به رکورد در لحظه. API شما آنلاین است. گزارش شبانه آفلاین است. این دو دنیای جدا هستند. Process data in bulk as one job — not record by record in real time. Your API is online. The nightly report is offline. These are two different worlds.

نکته کلیدی: سیستم آنلاین منتظر جواب یک درخواست می‌ماند. شغل دسته‌ای یک ورودی بزرگ می‌گیرد، کار را تمام می‌کند، و یک خروجی می‌سازد. هیچ کاربری پشت صفحه منتظر نیست. The central idea: an online system waits for one request. A batch job takes a large input, finishes the work, and writes an output. No user is waiting on the other side.

01

پردازش دسته‌ای چیست و چرا مهم است؟What is batch processing and why it matters

↗DDIA 2e · فصل ۱۱ — Batch ProcessingDDIA 2e · Ch. 11 — Batch Processing ↗FDE · فصل ۳ — معماری دادهFDE · Ch. 3 — Data Architecture

پردازش دسته‌ای یعنی داده را به‌صورت انبوه، در یک شغل، پردازش کنید. رکورد به رکورد در لحظه کار نمی‌کنید. کتاب Designing Data-Intensive Applications این را در برابر سیستم‌های آنلاین می‌گذارد: آنلاین یعنی درخواست می‌آید و جواب برمی‌گردد. آفلاین یعنی شغل شروع می‌شود، تمام ورودی را می‌خواند، و خروجی را می‌نویسد. Batch processing means you process data in bulk as one job. You do not handle each record in real time. Designing Data-Intensive Applications contrasts this with online systems: online is request and response. Offline is a job that reads all input and writes an output.

در معماری داده، این شغل یک تکه از کل تصویر است. معماری خوب قطعات رایج را عاقلانه انتخاب می‌کند، برای شکست آماده است، و سیستم‌ها را سست‌پیوند نگه می‌دارد. شغل دسته‌ای معمولاً همان قطعه‌ای است که دادهٔ عملیاتی را به دادهٔ تحلیلی تبدیل می‌کند — بدون اینکه API فروش را سنگین کند. In a data architecture, this job is one piece of a larger picture. Good architecture picks common parts wisely, plans for failure, and keeps systems loosely coupled. A batch job is often the piece that turns operational data into analytical data — without loading down the sales API.

یک شغل، یک خروجیOne job, one output

ساعت ۲ شب، همهٔ سفارش‌های دیروز خوانده می‌شوند. یک گزارش روزانه ساخته می‌شود.At 2 a.m., all of yesterday's orders are read. One daily report is built.

ورودی بزرگA large input

شغل یک فایل، یک پوشه، یا یک جدول کامل را می‌گیرد. نه یک شناسه در URL.The job takes a file, a folder, or a whole table. Not one id in a URL.

بدون انتظار کاربرNo user waiting

اگر شغل ۲۰ دقیقه طول بکشد، کسی صفحه را رفرش نمی‌کند. زمان کل مهم است، نه تأخیر یک رکورد.If the job takes 20 minutes, nobody refreshes a page. Total time matters, not per-record latency.

خروجی قابل تکرارA repeatable output

همان ورودی باید همان خروجی را بدهد. اگر شغل خراب شد، دوباره اجرا می‌کنید.The same input should give the same output. If the job fails, you run it again.

مثال عددیA number example

فروشگاه شما روزی ۴۰۰٬۰۰۰ سفارش دارد. API هر سفارش را در ۱۰ میلی‌ثانیه می‌نویسد — این آنلاین است. گزارش شبانه همان ۴۰۰٬۰۰۰ سطر را یک‌جا جمع می‌زند و در ۸ دقیقه تمام می‌شود. اگر همان جمع را داخل هر درخواست API حساب کنید، تسویهٔ سبد خرید کند می‌شود.Your shop takes 400,000 orders a day. The API writes each order in 10 ms — that is online. The nightly report sums those 400,000 rows in one job and finishes in 8 minutes. If you compute that sum inside every API call, checkout gets slow.

.NET

برای یک بک‌اندکار .NET این یعنی: BackgroundService، Hangfire یا یک Azure Function زمان‌بندی‌شده. کنترلر MVC جای این کار نیست. درخواست HTTP باید کوتاه بماند. شغل دسته‌ای جدا اجرا می‌شود و نتیجه را در جدول گزارش یا فایل می‌نویسد.For a .NET backend dev this means: a BackgroundService, Hangfire, or a scheduled Azure Function. An MVC controller is the wrong place. Keep the HTTP request short. Run the batch job aside and write the result to a report table or a file.

02

چرا کار تحلیلی به ذخیرهٔ دیگری نیاز دارد؟Why analytical workloads need different storage

↗DDIA 2e · فصل ۴ — Storage and RetrievalDDIA 2e · Ch. 4 — Storage and Retrieval ↗همین مجموعه · ایندکس‌هاThis series · Indexes

نیمهٔ دوم فصل ۴ کتاب DDIA می‌گوید کار تحلیلی به چیدمان دیگری روی دیسک نیاز دارد. سیستم آنلاین (OLTP) سطر را کامل می‌خواهد: یک سفارش، همهٔ ستون‌ها. شغل تحلیلی معمولاً چند ستون را روی میلیون‌ها سطر جمع می‌زند. برای آن، ذخیرهٔ ستون‌محور بهتر است. The second half of DDIA Chapter 4 says analytical work needs a different layout on disk. An online system (OLTP) wants a whole row: one order, every column. An analytical job usually sums a few columns across millions of rows. For that, column-oriented storage is better.

درخت B، LSM و ایندکس هش را در صفحهٔ ایندکس‌ها دیدید. اینجا آن‌ها را تکرار نمی‌کنیم. نکتهٔ تازه این است: همان موتور سطر‌محور که سفارش را سریع پیدا می‌کند، برای «جمع فروش سال» پرهزینه است. You already met B-trees, LSM-trees, and hash indexes on the Indexes page. We will not teach them again. The new point: the same row store that finds one order fast is expensive for “sum of sales this year.”

سطر‌محور — OLTPRow-oriented — OLTP

هر سطر کنار هم روی دیسک می‌نشیند. خواندن یک سفارش ارزان است. خواندن یک ستون از ۱۰ میلیون سطر یعنی بیشترِ جدول را لمس کنید.Each row sits together on disk. Reading one order is cheap. Reading one column from 10 million rows means you touch most of the table.

ستون‌محور — تحلیلColumn-oriented — analytics

هر ستون در فایل خودش ذخیره می‌شود. موتور فقط ستون Amount را می‌خواند. فشرده‌سازی هم بهتر کار می‌کند، چون مقادیر شبیه هم کنار هم هستند.Each column lives in its own file. The engine reads only Amount. Compression also works better, because similar values sit together.

کدام خانه‌ها خوانده می‌شوند؟Which cells get read?

جدول کوچک زیر ۴ ستون و ۶ سطر دارد. کوئری فقط جمع Amount را می‌خواهد. سطر‌محور تقریباً همه را می‌خواند. ستون‌محور فقط یک ستون را.The tiny table below has 4 columns and 6 rows. The query only wants SUM(Amount). A row store reads almost everything. A column store reads one column.

۶ سطر × ۴ ستون = ۲۴ خانه. سطر‌محور هر ۲۴ خانه را لمس می‌کند.6 rows × 4 columns = 24 cells. The row store touches all 24.

چرا برای شغل دسته‌ای مهم استWhy this matters for batch

شغل تحلیلی اغلب روی انبار داده یا موتور ستونی اجرا می‌شود، نه روی SQL Server عملیاتی شما. فصل ۴ همچنین از کامپایل کوئری، برداری‌سازی (Vectorization)، نمای مادّی‌شده و مکعب داده حرف می‌زند. ایده یکی است: کار را برای اسکنِ بزرگ ارزان کنید، نه برای یک سطر.Analytical jobs often run on a warehouse or a columnar engine, not on your operational SQL Server. Chapter 4 also covers query compilation, vectorization, materialized views, and data cubes. The idea is the same: make a large scan cheap, not a single-row lookup.

.NET

اگر گزارش سنگین را مستقیم روی دیتابیس سفارش اجرا کنید، قفل و IO با API قاطی می‌شود. الگوی رایج: شب داده را به یک انبار (مثل Synapse، BigQuery، یا حتی یک دیتابیس فقط‌خواندنی ستونی) کپی کنید. برنامهٔ .NET گزارش را از آنجا می‌خواند.If you run a heavy report on the order database, locks and IO mix with the API. A common pattern: copy data at night into a warehouse (Synapse, BigQuery, or even a read-only columnar store). The .NET app reads reports from there.

از خط لولهٔ یونیکس تا شغل توزیع‌شدهFrom Unix pipelines to distributed batch jobs

↗DDIA 2e · فصل ۱۱DDIA 2e · Ch. 11 ↗FDE · فصل ۶ — StorageFDE · Ch. 6 — Storage

فصل ۱۱ با ابزارهای یونیکس شروع می‌کند. یک لاگ را با grep، awk، sort و uniq به هم وصل می‌کنید. هر برنامه یک کار کوچک می‌کند. خروجی یکی، ورودی بعدی است. این همان مدل ذهنی شغل دسته‌ای است. Chapter 11 starts with Unix tools. You chain a log through grep, awk, sort, and uniq. Each program does one small job. One output becomes the next input. That is the mental model of a batch job.

bash — simple log analysis
# How many paid orders per country yesterday?
cat orders.log \
  | grep 'status=paid' \
  | awk -F, '{print $3}' \
  | sort \
  | uniq -c

زنجیره بهتر از یک برنامهٔ غولA chain beats one giant program

هر مرحله را جدا تست می‌کنید. اگر sort کند است، فقط همان را عوض می‌کنید. کتاب همین را در برابر یک برنامهٔ سفارشی می‌گذارد.You test each step alone. If sort is slow, you replace only that step. The book sets this against one custom program.

مرتب‌سازی در برابر جمع در حافظهSorting vs in-memory aggregation

اگر همهٔ کلیدها در RAM جا شوند، یک دیکشنری کافی است. اگر جا نشوند، sort داده را به دیسک می‌ریزد و بعد گروه‌ها را می‌سازد. شغل‌های بزرگ همین کار را می‌کنند.If every key fits in RAM, a dictionary is enough. If not, sort spills to disk and then builds groups. Large jobs do the same thing.

وقتی داده از یک ماشین بزرگ‌تر می‌شود، همان ایده روی چند ماشین تکرار می‌شود. فایل‌ها روی یک سیستم فایل توزیع‌شده مثل HDFS می‌نشینند، یا روی یک ذخیرهٔ شیء مثل S3. شغل‌ها روی ماشین‌های جدا اجرا می‌شوند و یک هماهنگ‌کننده آن‌ها را زمان‌بندی می‌کند. When data no longer fits on one machine, the same idea repeats across machines. Files live on a distributed filesystem such as HDFS, or on an object store such as S3. Jobs run on separate machines. An orchestrator schedules them.

کجاWhere چه می‌خواندWhat it reads نکتهNote

مثالExample

لاگ یک روز ۸۰ گیگابایت است. روی لپ‌تاپ sort ساعت‌ها طول می‌کشد. روی یک خوشه، فایل به قطعه‌های ۱۲۸ مگابایتی شکسته می‌شود. هر قطعه روی یک ماشین جدا grep می‌شود. بعد نتایج با هم ادغام می‌شوند. ایده همان خط لوله است — فقط پهن‌تر.One day of logs is 80 GB. On a laptop, sort takes hours. On a cluster, the file is split into 128 MB pieces. Each piece is grepped on a different machine. Then the results merge. Same pipeline idea — just wider.

.NET

شما مجبور نیستید Hadoop بنویسید. همان مدل را با فایل‌های روزانه در Blob Storage و یک Job زمان‌بندی‌شده دارید. برنامه فایل را تکه‌تکه می‌خواند (PipeReader یا IAsyncEnumerable)، تبدیل می‌کند، و با SqlBulkCopy می‌نویسد. کل جدول را در RAM نکشید.You do not have to write Hadoop. You already have the same model with daily files in Blob Storage and a scheduled job. The app reads the file in chunks (PipeReader or IAsyncEnumerable), transforms them, and writes with SqlBulkCopy. Do not load the whole table into RAM.

MapReduce و موتورهای جریان دادهMapReduce and dataflow engines

↗DDIA 2e · فصل ۱۱ — مدل‌هاDDIA 2e · Ch. 11 — models ↗DDIA 1e · فصل ۱۰ (زمینه)DDIA 1e · Ch. 10 (context)

MapReduce همان خط لوله را روی یک خوشه استاندارد کرد. Map هر رکورد را به جفت کلید/مقدار تبدیل می‌کند. Shuffle همهٔ مقادیر یک کلید را پیش یک ماشین می‌برد. Reduce آن گروه را جمع می‌زند. موتورهای جدیدتر مثل Spark و Flink همین ایده را به یک گراف از عملگرها تبدیل کردند. MapReduce made that pipeline standard on a cluster. Map turns each record into a key/value pair. Shuffle sends every value for one key to the same machine. Reduce aggregates that group. Newer engines such as Spark and Flink turn the same idea into a graph of operators.

1Map

هر سفارش می‌شود (IR, 120). کار موازی و بدون هماهنگی است.Each order becomes (IR, 120). The work is parallel and needs no talk between workers.

2Shuffle

شبکه همهٔ کلیدهای IR را یک‌جا جمع می‌کند. این معمولاً گران‌ترین مرحله است.The network gathers every IR key in one place. This is often the most expensive step.

3Reduce

مقادیر هر کشور جمع می‌شوند: IR → 540. خروجی کوچک‌تر از ورودی است.Values for each country are summed: IR → 540. The output is smaller than the input.

موتورهای جریان داده (Dataflow) بین مرحله‌ها داده را بیشتر در حافظه نگه می‌دارند. لازم نیست بعد از هر Map یک فایل عظیم روی دیسک بنویسید. Join و GroupBy همان Shuffle را دارند، فقط با API تمیزتر — DataFrame یا یک زبان کوئری. Dataflow engines keep data in memory between stages more often. You do not have to write a huge file after every Map. Joins and grouping still shuffle, just with a cleaner API — a DataFrame or a query language.

pseudocode — map, shuffle, reduce
# input: 12 paid orders
map(order) -> emit(order.Country, order.Amount)

# shuffle groups by key
IR: [120, 90, 40, 80]
DE: [80, 60, 70]
US: [200, 50, 150, 30, 110]

reduce(country, amounts) -> emit(country, sum(amounts))
# IR=330  DE=210  US=540
.NET

معادل کوچک در C#: orders.GroupBy(o => o.Country).Select(g => new { g.Key, Total = g.Sum(x => x.Amount) }). روی یک ماشین این LINQ است. روی یک خوشه، همین GroupBy یک Shuffle در شبکه است. وقتی داده از RAM یک سرور رد شد، هزینه عوض می‌شود.The small C# version is orders.GroupBy(o => o.Country).Select(g => new { g.Key, Total = g.Sum(x => x.Amount) }). On one machine that is LINQ. On a cluster, the same GroupBy is a network shuffle. When data no longer fits in one server's RAM, the cost changes.

05

دادهٔ دسته‌ای کجا زندگی می‌کند؟Where batch data lives

↗FDE · فصل ۶ — Warehouse، Lake، LakehouseFDE · Ch. 6 — warehouse, lake, lakehouse

شغل دسته‌ای از جایی می‌خواند و جایی می‌نویسد. فصل ۶ سه مقصد رایج را جدا می‌کند. این‌ها برند نیستند؛ سه قرارداد درباره‌ی شکل داده، کیفیت، و اینکه چه کسی کوئری می‌زند. A batch job reads from somewhere and writes somewhere. Chapter 6 splits three common homes. These are not brands. They are three contracts about shape, quality, and who runs queries.

انبار دادهData warehouse

جداول تمیز، اسکیما مشخص، بهینه برای SQL تحلیلی. محل گزارش‌های مالی و داشبورد. معمولاً ستون‌محور است.Clean tables, a clear schema, built for analytical SQL. Home of finance reports and dashboards. Often columnar.

دریاچهٔ دادهData lake

فایل‌های خام روی ذخیرهٔ شیء: JSON، CSV، Parquet. ارزان است. اسکیما دیرتر اعمال می‌شود. خطر «باتلاق داده» هست اگر کاتالوگ نباشد.Raw files on object storage: JSON, CSV, Parquet. Cheap. Schema comes later. A lake becomes a swamp if there is no catalog.

LakehouseLakehouse

فایل‌های دریاچه به‌علاوهٔ جدول، تراکنش و اسکیما. هدف: یک جا هم ارزان باشد، هم قابل کوئری مثل انبار.Lake files plus tables, transactions, and schema. The goal: one place that is cheap and still queryable like a warehouse.

مثال مسیرA path example

شب، سفارش‌های SQL Server با یک فایل Parquet به S3 (دریاچه) می‌روند. صبح، یک شغل دوم همان فایل را به جدول fact_orders در انبار می‌ریزد. داشبورد فقط انبار را می‌بیند. فایل خام برای آموزش مدل یا بازرسی بعدی می‌ماند.At night, SQL Server orders land as a Parquet file on S3 (the lake). In the morning, a second job loads that file into fact_orders in the warehouse. The dashboard only sees the warehouse. The raw file stays for model training or later checks.

.NET

شما اغلب «تولیدکنندهٔ فایل» هستید، نه مالک انبار. یک Worker فایل را می‌نویسد، مسیر را در یک صف یا جدول کنترل ثبت می‌کند، و شغل بعدی آن را برمی‌دارد. ذخیرهٔ شیء را مثل دیسک محلی فرض نکنید: لیست کردن میلیون‌ها فایل کوچک گران است. فایل‌های درشت روزانه بهترند.You are often the file producer, not the warehouse owner. A worker writes a file, records the path in a queue or control table, and the next job picks it up. Do not treat object storage like a local disk: listing millions of tiny files is expensive. Fat daily files work better.

06

داده چطور وارد شغل می‌شود؟Getting data into a batch job

↗FDE · فصل ۷ — IngestionFDE · Ch. 7 — Ingestion

ورود داده (Ingestion) یعنی آوردن داده از سیستم مبدأ به جایی که شغل می‌تواند آن را بخواند. این با یکپارچه‌سازی کامل فرق دارد. دو تصمیم برای بک‌اندکار مهم است: کل جدول را برمی‌دارید یا فقط تغییرها را؟ و تبدیل را قبل از بارگذاری انجام می‌دهید یا بعد از آن؟ Ingestion means bringing data from a source system to a place the job can read. That is not the same as full integration. Two decisions matter for a backend dev: do you take a full snapshot or only the changes? And do you transform before load, or after?

تصویر کامل (Snapshot)Snapshot extraction

هر بار کل جدول را کپی می‌کنید. ساده است. برای جدول ۱۰ هزار سطری خوب است. برای ۴۰۰ هزار سفارش در روز، هر شب کل تاریخ را دوباره خواندن اسراف است.You copy the whole table every time. Simple. Fine for a 10,000-row table. For 400,000 orders a day, rereading all history every night is waste.

استخراج تفاضلیDifferential extraction

فقط سطرهای جدید یا عوض‌شده را می‌برید. معمولاً با UpdatedAt > last_run یا Change Tracking. سبک‌تر است، اما حذف‌ها و ساعت‌های ناهماهنگ را باید خودتان حل کنید.You take only new or changed rows. Often UpdatedAt > last_run or Change Tracking. Lighter, but you must handle deletes and clock skew yourself.

ETL ELT
ترتیبOrder استخراج → تبدیل → بارگذاریExtract → Transform → Load استخراج → بارگذاری → تبدیلExtract → Load → Transform
تبدیل کجا؟Where is transform? قبل از انبار، در شغل شماBefore the warehouse, in your job داخل انبار، با SQL موتورInside the warehouse, with its SQL
چه زمانی؟When? وقتی انبار ضعیف است یا داده باید قبل از ورود تمیز شودWhen the warehouse is weak, or data must be clean before entry وقتی انبار قوی است و می‌خواهید دادهٔ خام را هم نگه داریدWhen the warehouse is strong and you also want the raw copy

اندازهٔ دسته هم معامله دارد. دستهٔ خیلی کوچک یعنی سربار زیاد برای هر commit. دستهٔ خیلی بزرگ یعنی اگر شغل وسط کار بمیرد، باید حجم عظیمی را دوباره انجام دهید. برای ورود پیام‌ها، این صفحه فقط یک تضاد کوتاه می‌گوید: جریان بی‌کران است؛ دسته کران‌دار است. Batch size is also a trade-off. A tiny batch adds commit overhead. A huge batch means a crash forces a giant redo. For contrast only: a stream is unbounded; a batch is bounded.

c# — differential extract, then bulk load
var watermark = await control.GetLastSuccessAsync(jobName, ct);

var rows = await source.Orders
    .Where(o => o.UpdatedAt > watermark)
    .AsNoTracking()
    .ToListAsync(ct);                 // extract (differential)

var clean = rows
    .Where(o => o.Status == "Paid")
    .Select(ToFactRow)
    .ToList();                        // transform

await warehouse.BulkInsertAsync(clean, batchSize: 5000, ct);
await control.SaveWatermarkAsync(jobName, rows.Max(o => o.UpdatedAt), ct);
.NET

یک جدول کنترل با JobName، LastWatermark و Status نگه دارید. شغل باید ایدمپوتنت باشد: اجرای دوباره همان روز نباید سطر تکراری بسازد. SqlBulkCopy با چند هزار سطر در هر دسته معمولاً نقطهٔ شروع خوبی است. Push یعنی مبدأ داده را می‌فرستد؛ Pull یعنی شغل خودش می‌کشد — بیشتر شغل‌های شبانه Pull هستند.Keep a control table with JobName, LastWatermark, and Status. The job should be idempotent: a rerun of the same day must not create duplicates. SqlBulkCopy with a few thousand rows per batch is a decent start. Push means the source sends data; pull means the job fetches it — most nightly jobs pull.

کاربردهای واقعیReal-world batch use cases

↗DDIA 2e · فصل ۱۱ — Use CasesDDIA 2e · Ch. 11 — use cases

فصل ۱۱ چهار خانوادهٔ اصلی نشان می‌دهد. برای یک برنامه‌نویس بک‌اند، ETL آشناترین است. بقیه هم همان الگوی «ورودی بزرگ → خروجی مشتق» هستند. Chapter 11 shows four main families. For a backend programmer, ETL is the most familiar. The others are the same pattern: large input → derived output.

ETL

سفارش‌ها از SQL Server عملیاتی بیرون می‌آیند، ارز یکسان می‌شوند، و به جدول واقعیت می‌روند. این همان لولهٔ شبانه است.Orders leave operational SQL Server, money is normalized, and they land in a fact table. That is the nightly pipe.

تحلیلAnalytics

جمع فروش هر کشور، نرخ بازگشت، قیف تبدیل. کوئری روی انبار اجرا می‌شود، نه روی دیتابیس زنده.Sales by country, return rate, conversion funnel. The query runs on the warehouse, not on the live database.

یادگیری ماشینMachine learning

یک شغل شبانه ویژگی‌ها را می‌سازد: «این مشتری در ۳۰ روز چند خرید داشت؟» مدل روی آن فایل آموزش می‌بیند.A nightly job builds features: “how many purchases did this customer make in 30 days?” The model trains on that file.

دادهٔ مشتق برای سرویسServing derived data

رتبه‌بندی پرفروش‌ها یا کش پیشنهاد کالا یک‌بار در روز ساخته می‌شود. API فقط همان جدول آماده را می‌خواند.A bestseller ranking or a recommendation cache is built once a day. The API only reads that ready table.

مرز با آنلاینThe online boundary

اگر مدیر بخواهد «فروش همین الان»، شغل شبانه کافی نیست. آن‌وقت سراغ جریان داده می‌روید. ولی بیشتر گزارش‌های کسب‌وکار تأخیر چند ساعته را تحمل می‌کنند — و دسته ارزان‌تر و ساده‌تر است.If a manager wants “sales right now,” a nightly job is not enough. Then you look at streaming. But most business reports can wait a few hours — and batch is cheaper and simpler.

.NET

یک الگوی تمیز: API فقط سفارش را می‌نویسد. یک Hosted Service ساعت ۲ شب جدول DailySales را پر می‌کند. صفحهٔ ادمین همان جدول را می‌خواند. منطق گزارش داخل کنترلر پخش نمی‌شود.A clean pattern: the API only writes the order. A hosted service fills DailySales at 2 a.m. The admin page reads that table. Report logic does not leak into the controller.

کوئری تحلیلی چند ستون را روی میلیون‌ها سطر می‌خواند. ذخیرهٔ ستونی فقط همان ستون‌ها را از دیسک می‌آورد و بهتر فشرده می‌شود. ذخیرهٔ سطری برای خواندن یک سفارش کامل ساخته شده، نه برای اسکن بزرگ.An analytical query reads a few columns across millions of rows. A column store fetches only those columns and compresses them well. A row store is built to read one full order, not a large scan.

Join و GroupBy هم همین جابه‌جایی را دارند.After Map, every value for one key must reach the same Reduce. Shuffle moves and groups that data on the network. Joins and grouping do the same move.

A lake is raw files on object storage. A lakehouse tries to keep the cheap lake files and add warehouse schema and transactions.
