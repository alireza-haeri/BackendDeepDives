شاردینگ داده Data Sharding

وقتی یک سرور دیگر جواب نمی‌دهد — چطور داده‌ها را بین چندین ماشین پخش می‌کنید بدون اینکه همه‌چیز از هم بپاشد؟ When one server is no longer enough — how do you spread data across many machines without everything falling apart?

در فصل قبل، داده را داخل یک دیتابیس تقسیم کردیم. اینجا از مرزهای یک سرور عبور می‌کنیم: داده بین چندین ماشین مستقل پخش می‌شود تا ظرفیت و توان نوشتن فراتر از محدودیت‌های یک سرور برود. In the previous chapter, we partitioned data within one database. Here we cross the boundary of a single server: data is spread across multiple independent machines so capacity and write throughput exceed one server's limits.

01

شاردینگ چیست — و چرا اهمیت داردWhat sharding is — and why it matters

منبع: NoSQL Distilled، فصل ۴NoSQL Distilled, Ch. 4

شاردینگ یعنی تقسیم داده‌ها بین چند سرور مستقل. هر سرور فقط مسئول بخشی از داده‌هاست. وقتی حجم داده یا تعداد درخواست‌ها از توان یک سرور بیشتر شود، شاردینگ تنها راه باقی‌مانده است. Sharding means splitting data across multiple independent servers. Each server is responsible for only a portion of the data. When data volume or request rate exceeds one server's capacity, sharding is the only option left.

خواندن‌ها و نوشتن‌ها سریع می‌شوندReads and writes speed up

هر سرور فقط بخشی از داده را دارد. کوئری‌ها فقط به سرورِ مربوط می‌روند. نوشتن‌ها بین سرورها پخش می‌شوند. Each server holds only a portion of the data. Queries go only to the relevant server. Writes are spread across servers.

پیچیدگی اضافه می‌شودComplexity increases

JOIN بین شاردها سخت است. تراکنش‌های بین‌شاردی پیچیده‌اند. به یک لایهٔ مسیریابی نیاز دارید. JOINs across shards are hard. Cross-shard transactions are complex. You need a routing layer.

.NET

در دنیای .NET و SQL Server، ما عادت داریم یک Connection String داشته باشیم. شاردینگ یعنی این سادگی از بین می‌رود: کد C# شما باید بداند هر کلید به کدام سرور می‌رود، یا از یک لایهٔ واسط استفاده کنید. SQL Server خودش شاردینگ ندارد — برای شاردینگ واقعی سراغ Cosmos DB، Cassandra یا MongoDB می‌روید. In the .NET and SQL Server world, we're used to one Connection String. Sharding kills that simplicity: your C# code must know which server holds each key, or you use an intermediary layer. SQL Server has no native sharding — for real sharding you go to Cosmos DB, Cassandra, or MongoDB.

02

شاردینگ در برابر تکثیر — دو ابزار متفاوتSharding vs replication — two different tools

منبع: NoSQL Distilled، فصل ۴NoSQL Distilled, Ch. 4

این دو مفهوم اغلب قاطی می‌شوند. بیایید یک‌بار برای همیشه از هم جدا کنیم: These two concepts are often confused. Let's separate them once and for all:

تکثیر (Replication)Replicationشاردینگ (Sharding)Sharding
دادهDataهمهٔ داده در همهٔ سرورهاAll data on all serversبخشی از داده در هر سرورPart of data on each server
هدفGoalامنیت + سرعت خواندنSafety + read speedظرفیت + سرعت نوشتنCapacity + write speed
تشبیهAnalogyسه نسخه از یک کتاب در سه کتابخانهThree copies of one book in three librariesکتابخانهٔ بزرگ تقسیم‌شده بین چهار شعبهA big library split among four branches

قاعدهٔ سرانگشتی: در سیستم‌های واقعی، این دو را ترکیب می‌کنید. داده را شارد می‌کنید تا جا شود، سپس هر شارد را تکثیر می‌کنید تا اگر سروری از کار افتاد، داده‌های آن شارد از دست نرود. مثلاً ۴ شارد × ۳ کپی = ۱۲ سرور. Rule of thumb: in real systems, you combine both. You shard the data so it fits, then replicate each shard so if a server dies, that shard's data isn't lost. E.g., 4 shards × 3 copies = 12 servers.

چطور شاردِ هر داده را انتخاب کنیم؟How to choose which shard gets the data?

منبع: DDIA، فصل ۶DDIA, Ch. 6

دو راه اصلی: بازهٔ کلید (مثل دایره‌المعارف) یا هشِ کلید (توزیع یکنواخت). بیایید هر دو را امتحان کنیم: Two main approaches: key range (like an encyclopedia) or hash of key (even distribution). Let's try both:

یک کلید بنویسید و «بنویس» را بزنید.Type a key and press "Write".

هش — توزیع یکنواختHash — even distribution

مزیت: توزیع کاملاً یکنواخت، بدون Hot Spot.
عیب: کوئری‌های بازه‌ای دیگر کار نمی‌کنند. Pro: perfectly even distribution, no hot spots.
Con: range queries break completely.

بازه — مرتب اما خطرناکRange — sorted but risky

مزیت: کوئری‌های بازه‌ای سریع‌اند.
عیب: اگر بیشتر کلیدها با یک حرف شروع شوند، یک سرور داغ می‌کند (Hot Spot). Pro: range queries are fast.
Con: if most keys start with one letter, one server becomes a hot spot.

04

هش سازگار — حلقه‌ای که با تغییر نمی‌شکندConsistent hashing — the ring that doesn't break

منبع: System Design Interview، فصل ۵System Design Interview, Ch. 5

روش «هش ساده» (hash % N) یک مشکل بزرگ دارد: اگر یک سرور اضافه یا کم شود، N تغییر می‌کند و بیشتر کلیدها جابه‌جا می‌شوند. هش سازگار این مشکل را با یک «حلقه» حل می‌کند: The "naive hash" method (hash % N) has a huge problem: if you add or remove a server, N changes and most keys move. Consistent hashing solves this with a "ring":

حلقهٔ هش سازگار — سرور D را اضافه و حذف کنیدConsistent hash ring — add and remove server D
هش ساده (hash % N)Naive hash (hash % N)
~67%
هش سازگار (Ring)Consistent hash (Ring)
0 / 5
سرور D را اضافه (و دوباره حذف) کنید تا تفاوت را ببینید. در هش ساده بیشتر کلیدها جابه‌جا می‌شوند، اما در هش سازگار معمولاً فقط یکی! Add (then remove again) server D to see the difference. With naive hash most keys move, but with consistent hashing usually only one!

گره‌های مجازی (Virtual Nodes): در عمل، هر سرور فیزیکی چندین بار روی حلقه قرار می‌گیرد (مثلاً ۱۵۰ بار). این کار توزیع بار را یکنواخت‌تر می‌کند و وقتی سروری اضافه/کم می‌شود، بار به‌تدریج منتقل می‌شود نه یکباره. Virtual Nodes: in practice, each physical server appears on the ring multiple times (e.g., 150 times). This makes load distribution more even, and when a server is added/removed, load transfers gradually, not all at once.

05

توازن مجدد پارتیشن‌هاRebalancing partitions

منبع: DDIA، فصل ۶DDIA, Ch. 6

وقتی سرور جدیدی اضافه می‌شود، داده‌ها باید دوباره پخش شوند. بیایید «تعداد ثابت پارتیشن» را ببینیم: When a new server arrives, data must be redistributed. Let's see "fixed number of partitions":

توازن مجدد — ۱۲ پارتیشن بین سرورهاRebalancing — 12 partitions across servers
سرور جدید اضافه کنید تا ببینید پارتیشن‌ها چطور (با حداقل جابه‌جایی) منتقل می‌شوند. Add a new server to watch partitions migrate with minimal movement.

تعداد ثابت پارتیشن‌هاFixed number of partitions

از روز اول مثلاً ۱۰۰۰ پارتیشن می‌سازید. وقتی سرور جدید می‌آید، فقط چند پارتیشن کامل منتقل می‌شود. ساده و قابل‌پیش‌بینی. Redis Cluster و Elasticsearch این کار را می‌کنند. You create 1000 partitions from day one. When a new server arrives, only a few whole partitions move. Simple and predictable. Redis Cluster and Elasticsearch do this.

پارتیشن‌بندی پویاDynamic partitioning

وقتی پارتیشنی بزرگ‌تر از حد مجاز شد، نصف می‌شود. وقتی خیلی کوچک شد، ادغام می‌شود. HBase و MongoDB این کار را می‌کنند. When a partition exceeds a limit, it splits. When too small, it merges. HBase and MongoDB do this.

ایندکس محلی (Local)Local index

هر شارد ایندکس خودش را دارد. برای جست‌وجو، باید به همهٔ شارد‌ها درخواست بفرستید و نتایج را جمع کنید. نوشتن سریع، خواندن کند. Each shard has its own index. To search, you must query all shards and merge results. Writes fast, reads slow.

ایندکس سراسری (Global)Global index

یک ساختار ایندکس جداگانه، کلمهٔ جست‌وجو را به شارد درست نگاشت می‌کند. خواندن سریع، نوشتن کندتر. A separate index structure maps the search term to the right shard. Reads fast, writes slower.

07

تکثیر شاردها — Leader-FollowerReplicating shards — Leader-Follower

منبع: DDIA، فصل ۵DDIA, Ch. 5

هر شارد به تنهایی یک نقطهٔ شکست است. پس هر شارد را تکثیر می‌کنیم. بیایید الگوی Leader-Follower را ببینیم: Each shard alone is a single point of failure. So we replicate each shard. Let's see the Leader-Follower pattern:

نوشتن به Leader، کپی به FollowerهاWrite to Leader, copy to Followers
LEADER
→async →replicate
FOLLOWER 1
FOLLOWER 2
دکمهٔ «نوشتن» را بزنید تا ببینید داده اول به Leader می‌رود، سپس با کمی تأخیر به Followerها کپی می‌شود. Press "New write" to see data go to Leader first, then copy to Followers with a slight delay.

لیدر-فالوئرLeader-Follower

یک لیدر قابل‌نوشتن + چند فالوئر فقط‌خواندنی. اگر لیدر بمیرد، فالوئر ارتقا می‌یابد. One writable leader + read-only followers. If leader dies, a follower is promoted.

چندلیدرهMulti-Leader

چند سرور قابل نوشتن در دیتاسنترهای مختلف. عالی برای سرعت، اما نیاز به حل تعارض دارد. Multiple writable servers in different data centers. Great for speed, but needs conflict resolution.

بدون لیدرLeaderless

کلاینت مستقیماً در چند سرور می‌نویسد. خواندن با Quorum. مثل Dynamo و Cassandra. Client writes to multiple servers directly. Reads with Quorum. Like Dynamo and Cassandra.

۱. سمت کلاینت1. Client-side

کلاینت نقشهٔ شاردها را دارد و مستقیم به سرور درست وصل می‌شود. Client has the shard map and connects directly to the right server.

۲. پروکسی / روتر2. Proxy / Router

کلاینت به Gateway می‌فرستد، پروکسی مسیریابی می‌کند. مثل Mongos یا Redis Cluster proxy. Client sends to Gateway, proxy routes. Like Mongos or Redis Cluster proxy.

۳. پرش بین گره‌ها3. Node-hopping

کلاینت به هر سروری وصل می‌شود؛ اگر کلید را نداشت، درخواست را فوروارد می‌کند. مثل Cassandra. Client connects to any server; if it doesn't have the key, it forwards. Like Cassandra.

جمع‌بندی: طراحی یک KV Store توزیع‌شدهPutting it together: Distributed KV Store

منبع: System Design Interview، فصل ۶System Design Interview, Ch. 6

شما شاردینگ (با هش سازگار) را با تکثیر (لیدر-فالوئر) ترکیب می‌کنید. حالا با قضیهٔ CAP روبرو می‌شوید: You combine sharding (consistent hashing) with replication (leader-follower). Now you face the CAP theorem:

│                   Shard-2 (Leader + 2 Followers)

└── Consistent Hash Ring decides which shard

// Read:  Client → Router → hash(key) → Shard Leader (or Follower)

.NET

به عنوان توسعه‌دهندهٔ بک‌اند، معمولاً این سیستم‌ها را از صفر نمی‌سازید، بلکه از دیتابیس‌هایی مثل Redis Cluster، Cassandra یا MongoDB استفاده می‌کنید. اما درک این مفاهیم به شما کمک می‌کند تا بدانید چرا در زمان قطعی شبکه، دیتابیس شما گاهی داده‌های قدیمی را برمی‌گرداند یا نوشتن را رد می‌کند. As a backend developer, you usually don't build these from scratch; you use databases like Redis Cluster, Cassandra, or MongoDB. But understanding these concepts helps you know why your database sometimes returns stale data or rejects writes during a network outage.

خودآزمایی — می‌توانید این‌ها را بلند جواب بدهید؟Self-check — can you answer these out loud?

تکثیر یعنی کپی کردن همان داده‌ها در چند جا برای امنیت و سرعت خواندن. شاردینگ یعنی تقسیم کردن داده‌های متفاوت بین چند سرور برای افزایش ظرفیت و سرعت نوشتن. Replication copies the same data to multiple places for safety and read speed. Sharding splits different data across multiple servers for capacity and write speed.
در hash % N، با اضافه یا حذف شدن یک سرور، N تغییر می‌کند و بیشتر کلیدها جابه‌جا می‌شوند (در دموی فصل ۴ حدود ۷۵٪!). اما در هش سازگار، فقط کسری کوچک از کلیدها — معمولاً یکی دو تا — جابه‌جا می‌شوند. With hash % N, when a server is added or removed, N changes and most keys move (~75% in the chapter 4 demo!). With consistent hashing, only a small fraction of keys — usually one or two — move.
ایندکس محلی نوشتن را سریع می‌کند اما برای خواندن باید به همهٔ شاردها درخواست بفرستید (Scatter-Gather). ایندکس سراسری خواندن را سریع می‌کند اما نوشتن نیازمند به‌روزرسانی همزمان شارد و ایندکس سراسری است. Local indexes make writes fast but require querying all shards to read (Scatter-Gather). Global indexes make reads fast but require updating both the shard and the global index on writes.
سیستم یکی از سرورهای فالوئر را به عنوان لیدر جدید ارتقا می‌دهد و بقیه فالوئرها شروع به کپی کردن از لیدر جدید می‌کنند. در این مدت کوتاه، ممکن است نوشتن در آن شارد متوقف شود. The system promotes one of the follower servers to be the new leader, and the other followers start copying from the new leader. During this brief window, writes to that shard might be halted.
شما باید بین در دسترس بودن (Availability) و سازگاری (Consistency) یکی را انتخاب کنید. یا سیستم را متوقف می‌کنید تا داده‌ها ناسازگار نشوند (CP)، یا به پذیرش درخواست ادامه می‌دهید و ریسک ناسازگاری موقت داده‌ها را می‌پذیرید (AP). You must choose between Availability and Consistency. Either you halt the system to prevent inconsistent data (CP), or you keep accepting requests and risk temporary data inconsistency (AP).
