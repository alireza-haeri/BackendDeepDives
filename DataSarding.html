شاردینگِ داده Data Sharding

وقتی یک دیتابیس دیگر از پسِ حجم، نرخِ نوشتن یا تعدادِ درخواست‌ها برنمی‌آید، داده را بین چند دیتابیسِ مستقل پخش می‌کنیم. اما در عوض، مسیریابی، تراکنش و نگهداری را هم واردِ بازی می‌کنیم. When one database can no longer handle the data volume, write rate, or request load, we distribute data across independent databases. In return, routing, transactions, and operations become our responsibility.

پیام اصلی: شاردینگ «ایندکسِ بزرگ‌تر» نیست و جایگزینِ پارتیشن‌بندیِ داخلِ یک دیتابیس هم نیست؛ یک تصمیمِ معماری برای scale-out است. The central idea: sharding is not a bigger index, nor a drop-in replacement for table partitioning; it is an architectural decision for scale-out.

01

شاردینگ دقیقاً چیست؟What exactly is sharding?

↗Microsoft · Sharding patternMicrosoft · Sharding pattern ↗MongoDB · ShardingMongoDB · Sharding

شاردینگ یعنی تقسیمِ افقیِ داده بین چند دیتابیس یا نودِ مستقل. هر shard یک زیرمجموعهٔ جدا از داده را نگه می‌دارد و schema معمولاً بین shardها یکسان است. برای اینکه درخواست به مقصد درست برسد، یک router، proxy یا خودِ موتورِ دیتابیس باید از shard key استفاده کند. Sharding is horizontal distribution of data across multiple independent databases or nodes. Each shard owns a disjoint subset of the data, usually with the same schema. A router, proxy, or the database engine uses a shard key to find the right destination.

Important distinction

«Partition» واژه‌ای عمومی برای تکه‌تکه‌کردن داده است؛ «table partitioning» معمولاً داخل یک دیتابیس انجام می‌شود، اما «sharding» داده را بین چند دیتابیس یا نود توزیع می‌کند. مرز این دو در محصولات مختلف ممکن است متفاوت نام‌گذاری شود، پس همیشه معماری واقعی موتور را بررسی کنید.“Partition” is a broad term. Table partitioning usually keeps the data inside one database, while sharding distributes it across databases or nodes. Product terminology varies, so verify the actual architecture of the platform you use.

02

چه زمانی شاردینگ منطقی است؟When does sharding make sense?

شاردینگ اولین ابزارِ کندیِ یک query نیست. قبل از آن، schema، ایندکس، execution plan، cache، read replica و table partitioning را بررسی کنید. شاردینگ زمانی معنا پیدا می‌کند که محدودیتِ یک نمونه واقعاً گلوگاه باشد و scale-up دیگر کافی یا اقتصادی نباشد.Sharding is not the first tool for a slow query. Check schema, indexes, execution plans, caching, read replicas, and table partitioning first. Sharding becomes reasonable when a single instance is the real bottleneck and scaling up is no longer sufficient or economical.

نشانه‌های مناسبSignals that may justify it

  • حجمِ کل داده از ظرفیتِ ذخیره‌سازی یا working set یک نمونه عبور می‌کند.The total data or working set exceeds one instance's practical capacity.
  • نرخِ نوشتن یا concurrency از توانِ یک نمونه بیشتر شده و replica فقط مشکلِ خواندن را حل می‌کند.Write throughput or concurrency exceeds one instance, and replicas do not solve write pressure.
  • بیشتر درخواست‌ها ذاتاً به یک tenant، customer یا account محدودند.Most requests are naturally scoped to one tenant, customer, or account.

نشانه‌های نامناسبSignals to stop and reconsider

  • مشکل فقط یک query بد یا ایندکسِ ناقص است.The problem is one bad query or a missing index.
  • گزارش‌ها و joinهای سراسری، بیشترِ workload را تشکیل می‌دهند.Global reports and cross-entity joins dominate the workload.
  • تراکنش‌های شما مرتباً باید چند shard را هم‌زمان و اتمیک تغییر دهند.Transactions frequently need atomic writes across several shards.
Decision order

اندازه‌گیری → بهینه‌سازی → scale-up → read scale → sharding. این ترتیب قانونِ مطلق نیست، اما کمک می‌کند شاردینگ را برای مشکلی به کار نبرید که با یک ایندکس یا طراحی query حل می‌شود.Measure → optimize → scale up → read scale → shard. This is not an absolute law, but it prevents using sharding for a problem an index or query change would solve.

03

Shard key؛ مهم‌ترین تصمیم طراحیThe shard key: the most important design decision

↗MongoDB · انتخاب shard keyMongoDB · Choosing a shard key↗Azure Architecture · ShardingAzure Architecture · Sharding

Shard key ستون یا ترکیبی از ستون‌هاست که تعیین می‌کند یک row یا entity کجا قرار بگیرد. کلید خوب هم توزیعِ بار را متعادل می‌کند و هم queryهای پرتکرار را به shardهای کمی هدایت می‌کند؛ هیچ کلیدی برای همهٔ workloadها بهترین نیست.A shard key is the field or compound key that determines where a row or entity lives. A good key balances load and keeps common queries targeted; no key is best for every workload.

1توزیع‌پذیریDistributable

مقادیر کافی و توزیع نسبتاً یکنواخت داشته باشد؛ کلیدی مثل Status با سه مقدار معمولاً برای توزیع مناسب نیست.It should have enough values and reasonably even distribution; a three-value field such as Status is usually a poor distribution key.

2قابلِ مسیریابیRoutable

در queryهای اصلی حضور داشته باشد تا router مجبور نشود به همهٔ shardها broadcast کند.It should appear in important queries so the router can avoid broadcasting to every shard.

3پایدار و قابلِ انتقالStable and movable

تا حد امکان تغییر نکند؛ تغییرِ کلید یعنی انتقال entity و پیچیدگیِ consistency در زمان جابه‌جایی.It should rarely change; changing it can mean moving an entity and coordinating consistency during the move.

الگوی چندمستاجریMulti-tenant pattern

اگر تقریباً هر درخواست یک TenantId دارد، شاردکردن بر اساس tenant می‌تواند بیشتر queryها را تک‌شاردی نگه دارد. اما یک tenant خیلی بزرگ می‌تواند hot shard بسازد؛ برای این حالت، کلید مرکب یا تقسیمِ tenantهای بزرگ لازم می‌شود.If almost every request has a TenantId, tenant-based sharding can keep most queries single-shard. But one very large tenant can create a hot shard; large tenants may need a compound key or special treatment.

توزیع خوب کافی نیستEven distribution is not enough

کلیدی که عالی پخش می‌شود اما در queryها دیده نمی‌شود، فقط fan-out تولید می‌کند. workload، الگوی join، اندازهٔ entity و عملیاتِ آینده را هم کنارِ cardinality بسنجید.A key that distributes evenly but never appears in queries only creates fan-out. Evaluate workload, joins, entity size, and future operations alongside cardinality.

Scatter/gather is not free

در fan-out، زمانِ پاسخ معمولاً به کندترین shard به‌علاوهٔ هزینهٔ شبکه و merge نزدیک می‌شود. یک shardِ کند، retry یا hotspot می‌تواند tail latency کل request را بالا ببرد؛ موازی‌کردنِ درخواست‌ها این هزینه را حذف نمی‌کند.For fan-out, response time is often bounded by the slowest shard plus network and merge cost. A slow shard, retry, or hotspot can raise the request's tail latency; parallelism does not make that cost disappear.

06

JOIN، تراکنش و consistency در مرز shardJoins, transactions, and consistency across shards

تا وقتی عملیات در یک shard بماند، می‌توان از transaction و constraintهای همان دیتابیس استفاده کرد. وقتی مرز shard را رد می‌کنیم، شبکه، failure و هماهنگیِ چند منبع واردِ مدل می‌شوند.Inside one shard, the database can provide its local transactions and constraints. Once an operation crosses a shard boundary, network failures and multi-resource coordination become part of the model.

طراحیِ خوبThe good path

  • درخواست را با shard key شروع کنید و transaction را داخل همان shard نگه دارید.Start the request with the shard key and keep the transaction inside that shard.
  • جدول‌های همیشه‌همراه را با همان کلید توزیع کنید تا co-located شوند.Distribute tables that are always joined with the same key so they can be co-located.
  • دادهٔ کوچک و عمومی را در صورت پشتیبانیِ محصول، reference/replicated کنید.Replicate small, mostly-static reference data when the platform supports it.

وقتی مجبور به cross-shard هستیدWhen cross-shard is unavoidable

  • fan-out query و merge در یک لایهٔ مشخص انجام دهید؛ آن را پنهان و بی‌هزینه فرض نکنید.Make fan-out and merge explicit in one layer; do not pretend they are free.
  • برای workflow چندمرحله‌ای، Saga، outbox و idempotency را بررسی کنید.For multi-step workflows, evaluate sagas, an outbox, and idempotency.
  • دو-فازی‌کردن تراکنش ممکن است لازم باشد، اما latency و failure modeهای خودش را دارد.Two-phase commit may be necessary, but it adds latency and failure modes of its own.

.NET

در EF Core، یک DbContext معمولاً به یک connection و در نتیجه به یک shard متصل است. یک context را بی‌خبر بین shardها نچرخانید. ابتدا با یک ShardResolver مقصد را پیدا کنید، connection همان shard را بسازید و بعد context را ایجاد کنید. اگر چند context لازم شد، مرز transaction و retry را صریح طراحی کنید.In EF Core, a DbContext normally represents one connection and therefore one shard. Do not silently move one context between shards. Resolve the destination first, create that shard's connection, then create the context. If several contexts are needed, design transaction and retry boundaries explicitly.

عملیاتِ واقعی: rebalancing، جابه‌جایی و .NETOperations: rebalancing, movement, and .NET

اضافه‌کردن shard فقط ساختنِ یک دیتابیس جدید نیست. باید schema را deploy کنید، map را به‌روز کنید، بخشی از داده را منتقل کنید، در زمان move درخواست‌های هم‌زمان را کنترل کنید و بعد صحتِ شمارش و routeها را بسنجید.Adding a shard is more than creating a database. You must deploy the schema, update the map, move data, handle concurrent requests during the move, and verify counts and routes afterward.

In production, the resolver needs secret management, bounded timeouts and retries, shard-aware telemetry, and protection against stale maps during rebalancing. Run EF migrations for every shard through a controlled pipeline.

خودآزمایی — قبل از شاردکردن جواب بدهیدSelf-check — answer before you shard

اگر پاسخ یک سؤال را نمی‌دانید، به همان بخش برگردید. هدف این نیست که اسم ابزارها را حفظ کنید؛ باید بتوانید هزینه و مسیرِ یک request را توضیح دهید.If you cannot answer one, return to that section. The goal is not memorizing product names; it is explaining the cost and path of a request.

Shard مالکِ یک زیرمجموعهٔ متفاوت از داده است؛ replica کپیِ همان زیرمجموعه است. سه shard می‌توانند داده را بین خود تقسیم کنند و هرکدام دو replica داشته باشند.A shard owns a different subset of data; a replica copies that same subset. Three shards can divide the data while each has two replicas.
router ممکن است مجبور شود query را به همهٔ shardها بفرستد، پاسخ‌ها را merge کند و کندترین مسیر را منتظر بماند. بعضی محصولات به‌دلیل metadata یا index اطلاعات بیشتری دارند، اما نباید targeted بودن را بدون بررسیِ محصول فرض کرد.The router may broadcast the query to every shard, merge the results, and wait for the slowest path. Products may have extra metadata or indexes, but do not assume targeting without checking the platform.
توزیعِ بارِ مناسب، حضور در queryهای پرتکرار، ثبات، cardinality کافی و سازگاری با joinهای مهم. فقط یکنواختیِ تعدادِ سطرها کافی نیست؛ hotspot و الگوی دسترسی هم مهم‌اند.It balances load, appears in important queries, is stable, has enough cardinality, and fits important joins. Even row counts alone are not enough; hotspots and access patterns matter.
چون commit، timeout، retry و failure دیگر به یک منبع محدود نیستند. 2PC می‌تواند atomicity بدهد اما هماهنگی و latency اضافه می‌کند؛ برای workflowهای طولانی، Saga و outbox اغلب گزینهٔ مناسب‌تری برای بررسی‌اند.Commit, timeout, retry, and failure now span multiple resources. 2PC can provide atomicity but adds coordination and latency; for long workflows, sagas and an outbox are often worth evaluating.
بعد از resolveکردنِ shard مقصد و با connection همان shard. context باید عمر و transaction مشخص داشته باشد؛ connection را بر اساس ورودیِ غیرقابل‌اعتماد بدون اعتبارسنجی به هر مقصدی باز نکنید.After resolving the destination shard, using that shard's connection. Give the context and transaction explicit lifetimes, and never open arbitrary destinations from unvalidated input.
